# Agent365 S2S Sample Design

## Goal

Add a self-contained .NET sample that demonstrates exporting Microsoft Agent 365 telemetry through the service-to-service (S2S) endpoint. The sample will manually create InvokeAgent, Inference, and ExecuteTool spans without depending on Agents Framework, an LLM, or an external tool.

The sample will mirror the authentication and telemetry scenario demonstrated by `microsoft/opentelemetry-distro-python` PR 217 while using the .NET Microsoft OpenTelemetry distro and Agent365 SDK contracts.

## Location and Project Shape

Create a .NET 8 console application at:

`examples/Microsoft.OpenTelemetry.Agent365.S2S.Demo`

Add the project to `Microsoft.OpenTelemetry.slnx`. The sample will reference the repository's local `Microsoft.OpenTelemetry` project so it always exercises the current source tree.

The sample will contain:

- `Program.cs`: configuration, telemetry setup, span orchestration, flushing, and user-facing output.
- `S2STokenProvider.cs`: S2S token exchange, caching, and tenant validation.
- Typed configuration classes for binding and validation.
- `appsettings.example.json`: tracked configuration schema with placeholders.
- `appsettings.json`: local configuration containing real credentials and excluded by `.gitignore`.
- `README.md`: setup, configuration, execution, expected logs, and troubleshooting.

No ASP.NET host, Agents Framework package, Azure OpenAI client, or external tool client will be used.

## Configuration

The sample will load `appsettings.json` from its content root and allow normal .NET configuration overrides from environment variables. Real credentials may be placed in the local file, but the file must not be committed.

The configuration schema will retain the Agent365 demo's service connection shape where practical:

```json
{
  "Connections": {
    "ServiceConnection": {
      "Settings": {
        "AuthorityEndpoint": "https://login.microsoftonline.com",
        "ClientId": "<blueprint-app-client-id>",
        "ClientSecret": "<blueprint-app-client-secret>",
        "TenantId": "<tenant-id>"
      }
    }
  },
  "Agent365": {
    "AgentAppInstanceId": "<agent-app-instance-id>",
    "AgentId": "<onboarded-agent-id>",
    "ClusterCategory": "production"
  }
}
```

`Agent365:AgentId` may default to `Agent365:AgentAppInstanceId`. All required values will be validated at startup. Empty values and unchanged `<...>` placeholders will produce actionable errors.

## S2S Token Generation

`S2STokenProvider` will implement the token resolver required by the Microsoft OpenTelemetry Agent365 exporter:

```csharp
Task<string?> ResolveAsync(string agentId, string tenantId)
```

The provider will perform the same S2S exchange as the Python sample:

1. Create an MSAL confidential client for the blueprint application.
2. Acquire an Azure AD token-exchange token using the agent app instance ID as the FIC path.
3. Create an MSAL confidential client for the agent app instance, using the first token as its client assertion.
4. Acquire an application token for the Agent365 observability resource's `/.default` scope.

The provider will reject resolver requests whose tenant differs from the configured credential tenant. Tokens will be cached per tenant and agent, using the returned expiration with a refresh buffer. Concurrent requests for the same key will not trigger duplicate token exchanges.

The provider will report which exchange stage failed and include safe MSAL error details. It will never log access tokens, client assertions, or client secrets.

## Telemetry Configuration

The sample will configure the Microsoft OpenTelemetry distro with:

- Console trace export, so generated spans are visible locally.
- Agent365 trace export.
- `Agent365.TokenResolver` set to `S2STokenProvider.ResolveAsync`.
- `Agent365.UseS2SEndpoint` set to `true`.
- Agent365 manual scope instrumentation enabled.
- Infrastructure instrumentation left disabled unless required by the distro.

Console logging will enable the Agent365 exporter category at a sufficiently detailed level to surface HTTP status and correlation ID information without exposing credentials.

The tracer provider will be force-flushed before process exit. A failed flush or export will produce a non-successful exit code where the SDK exposes a reliable failure signal; otherwise the exporter error will be clearly logged.

## Span Flow

One execution will generate a single nested trace:

1. `InvokeAgentScope`: represents the top-level invocation.
2. First `InferenceScope`: simulates selecting a tool.
3. `ExecuteToolScope`: simulates invoking a weather function and records structured arguments and results.
4. Second `InferenceScope`: simulates generating the final answer.
5. The final response is recorded on the InvokeAgent scope.

The sample will use deterministic IDs, messages, token counts, finish reasons, tool arguments, and tool results where that improves readability. Trace and span IDs remain generated by OpenTelemetry.

The sample will populate the Agent365 certification-relevant fields, including agent identity, tenant, request/session/conversation IDs, inference model/provider details, and tool details.

## Error Handling

The sample will fail fast for:

- Missing `appsettings.json`.
- Missing, empty, or placeholder configuration.
- Invalid tenant, client, instance, or agent identifiers.
- A resolver tenant that differs from the configured tenant.
- Any failed token-exchange stage.

Errors will state the failing configuration key or exchange stage and suggest the corrective action. Broad exception swallowing and success-shaped fallbacks are not permitted.

## Testing

Add focused automated tests covering:

- Configuration binding and placeholder rejection.
- Defaulting `AgentId` to `AgentAppInstanceId`.
- Tenant mismatch rejection.
- Successful three-stage token exchange through an injectable token-acquisition seam.
- Failure reporting for each token-exchange stage.
- Token caching, expiration buffer, and concurrent resolution.
- The expected InvokeAgent, Inference, ExecuteTool, Inference nesting and span attributes without live credentials.

Tests will not call Microsoft Entra or the Agent365 ingestion endpoint. Live S2S export will be documented as an opt-in manual verification using the local `appsettings.json`.

## Documentation and Security

The README will explain prerequisites, required Agent365 application permission, how to create the local configuration, how to run the sample, expected span/export logs, and common authentication failures.

The tracked example configuration will contain placeholders only. The real local configuration and generated telemetry storage will be ignored to prevent accidental credential or telemetry disclosure.

## Out of Scope

- Agents Framework or Microsoft 365 Agents SDK hosting.
- Real LLM inference.
- Real MCP or HTTP tool execution.
- Agentic-user authentication.
- A reusable production authentication library; the token provider is sample code demonstrating the S2S flow.
